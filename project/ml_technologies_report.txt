   1. DEMAND FORECASTING
================================================================================

   File: ml_models/demand_forecast.py
   API Endpoint: GET /api/forecast, GET /api/forecast/{category}

── 1.1 WHAT IT DOES ──────────────────────────────────────────────────────────

   The demand forecasting module predicts future product demand per category
   for the next 30 days. It produces daily predicted quantities that the
   dashboard visualizes alongside historical sales data, enabling store
   managers to anticipate stock needs and plan replenishment proactively.

── 1.2 TECHNOLOGIES USED ────────────────────────────────────────────────────

   Primary Model   : Exponential Smoothing (Holt-Winters)
   Fallback Model  : SARIMAX (Seasonal ARIMA with Exogenous Variables)
   Last Resort     : Seasonal Naive Method
   Library         : statsmodels (Python)

── 1.3 HOW EACH MODEL WORKS ─────────────────────────────────────────────────

   A) EXPONENTIAL SMOOTHING (HOLT-WINTERS)
   ────────────────────────────────────────
   Holt-Winters is a time-series forecasting method that decomposes a series
   into three components:

     • Level     — The baseline value of the series (average demand).
     • Trend     — The increasing or decreasing direction over time.
     • Seasonality — Repeating patterns at fixed intervals.

   In our implementation:
     - Trend mode: Additive (demand grows/shrinks by a constant amount).
     - Seasonal mode: Additive with a seasonal period of 7 (weekly cycles).
     - Initialization: "estimated" (statsmodels optimizes initial values).
     - Optimization: Enabled (optimized=True) — the library automatically
       finds the best smoothing parameters (alpha, beta, gamma).

   The model requires at least 2 full seasonal cycles (14 days of data) to
   fit weekly seasonality. If that's not available, it falls back to a
   simpler additive-trend-only model with no seasonal component.

   WHY HOLT-WINTERS:
     - Supermarket demand exhibits strong weekly patterns (e.g., higher sales
       on weekends, lower on Mondays). Holt-Winters naturally captures this.
     - It's computationally lightweight — can train per-category in under a
       second, making it suitable for on-demand retraining via the API.
     - It doesn't require stationarity (unlike raw ARIMA), so no need for
       complex differencing or unit root tests.
     - The additive seasonal mode handles zero-sales days gracefully without
       requiring log transformation.

   B) SARIMAX (Seasonal ARIMA with Exogenous Variables)
   ─────────────────────────────────────────────────────
   SARIMAX extends the classic ARIMA model to include seasonal components.
   ARIMA stands for AutoRegressive Integrated Moving Average:

     - AR (AutoRegressive): Uses past values to predict future values.
     - I  (Integrated): Differences the series to make it stationary.
     - MA (Moving Average): Uses past forecast errors in prediction.

   Our configuration:
     - Order: (1, 1, 1) — one AR lag, one differencing, one MA lag.
     - Seasonal Order: (1, 0, 1, 7) — seasonal AR(1), no seasonal
       differencing, seasonal MA(1), with a 7-day seasonal period.
     - enforce_stationarity=False — allows the model to handle non-stationary
       data more flexibly.
     - enforce_invertibility=False — relaxes MA constraints for robustness.
     - maxiter=100 — limits optimization iterations for speed.

   WHY SARIMAX AS FALLBACK:
     - SARIMAX can capture more complex autocorrelation structures that
       Holt-Winters might miss (e.g., lagged demand effects).
     - Acts as a safety net: if Holt-Winters fails to converge (which can
       happen with irregular or noisy data), SARIMAX provides an alternative.
     - The seasonal order (1,0,1,7) captures weekly patterns through a
       different mathematical formulation, providing model diversity.

   C) SEASONAL NAIVE METHOD
   ────────────────────────
   The simplest fallback: repeats the last 7 days of actual sales data as
   the forecast, with small random noise added (15% of the data's standard
   deviation) to avoid looking artificially flat.

   WHY SEASONAL NAIVE AS LAST RESORT:
     - If both statistical models fail (too little data, convergence errors,
       numerical issues), this guarantees a forecast is always returned.
     - Despite its simplicity, seasonal naive often outperforms complex models
       on very short time series. It's a well-known strong baseline in
       forecasting competitions.
     - The added noise makes the visualization look realistic rather than
       showing an obvious repeated pattern.

── 1.4 MODEL SELECTION STRATEGY ──────────────────────────────────────────────

   The system uses a cascading fallback strategy:
     1. Try Holt-Winters (best for weekly patterns) — requires ≥14 days
     2. If that fails, try SARIMAX — requires ≥14 days
     3. If both fail, use Seasonal Naive — works with any data length

   This ensures the system never returns an empty forecast regardless of
   data quality or quantity.

── 1.5 ALTERNATIVES CONSIDERED ───────────────────────────────────────────────

   - Prophet (by Meta): Excellent for business time-series but adds a heavy
     dependency (requires pystan/cmdstan). Rejected for portability reasons.
   - LSTM / Deep Learning: Overkill for category-level daily forecasting with
     <1 year of data. Would require GPU, more data, and longer training.
   - Simple Moving Average: Too simplistic — doesn't capture trends or
     weekly seasonality.

   2. CUSTOMER SEGMENTATION
================================================================================

   File: ml_models/customer_segmentation.py
   API Endpoint: GET /api/customers/segments (via ml.py routes)

── 2.1 WHAT IT DOES ──────────────────────────────────────────────────────────

   The customer segmentation module groups customers into 5 distinct segments
   based on their purchasing behavior. This enables targeted marketing,
   loyalty programs, and customer retention strategies. The segments are:

     • Champions         — Best customers: recent, frequent, high spenders
     • Loyal Customers   — Consistent buyers with good monetary value
     • Potential          — Moderate engagement, could be nurtured
     • At Risk           — Previously active, now declining
     • Lost              — Inactive or very low engagement

── 2.2 TECHNOLOGIES USED ────────────────────────────────────────────────────

   Analysis Framework : RFM Analysis (Recency, Frequency, Monetary)
   Clustering Model   : K-Means Clustering
   Feature Scaling    : StandardScaler
   Library            : scikit-learn

── 2.3 HOW IT WORKS ──────────────────────────────────────────────────────────

   STEP 1: RFM FEATURE COMPUTATION
   ─────────────────────────────────
   For each customer, three metrics are calculated from sales history:

     • Recency (R)   — Days since their last purchase. Lower = better.
                        Computed as: (reference_date - last_purchase_date).days
     • Frequency (F) — Number of unique transactions (sale_id count).
                        Higher = more engaged customer.
     • Monetary (M)  — Total amount spent (sum of total_price).
                        Higher = more valuable customer.

   WHY RFM:
     - RFM is the industry standard for retail customer analysis. It distills
       complex purchasing behavior into three interpretable dimensions.
     - It directly maps to actionable business questions:
       R → "Are they still active?"
       F → "How often do they buy?"
       M → "How much do they spend?"
     - No feature engineering guesswork — the three features are derived
       naturally from transactional data.

   STEP 2: STANDARDSCALER (Feature Scaling)
   ─────────────────────────────────────────
   Before clustering, all three RFM features are standardized using
   StandardScaler from scikit-learn:

     scaled_value = (value - mean) / standard_deviation

   WHY SCALING IS CRITICAL:
     - Monetary values might range from $5 to $5,000, while recency ranges
       from 1 to 365 days. Without scaling, monetary would dominate the
       distance calculations in K-Means, and recency/frequency would be
       effectively ignored.
     - StandardScaler (z-score normalization) centers each feature at mean=0
       with std=1, giving all three dimensions equal weight in clustering.
     - Preferred over MinMaxScaler because it's less sensitive to outliers
       (a single whale customer won't compress everyone else into a corner).

   STEP 3: K-MEANS CLUSTERING
   ──────────────────────────
   K-Means partitions customers into k=5 clusters by minimizing the within-
   cluster sum of squared distances (inertia):

     Parameters:
       - n_clusters = 5 (matches our 5 business segments)
       - random_state = 42 (reproducibility)
       - n_init = 10 (runs K-Means 10 times with different centroids and
                       picks the best result to avoid local minima)

   Algorithm:
     1. Initialize 5 random centroids in 3D RFM space.
     2. Assign each customer to the nearest centroid (Euclidean distance).
     3. Recompute centroids as the mean of assigned customers.
     4. Repeat steps 2-3 until convergence.

   WHY K-MEANS:
     - Fast and scalable — handles thousands of customers in milliseconds.
     - Produces spherical, well-separated clusters that map cleanly to
       business segments.
     - Easy to interpret: each cluster centroid represents the "average"
       customer profile for that segment.
     - The number of segments (k=5) aligns with established retail marketing
       frameworks (Champions/Loyal/Potential/At-Risk/Lost).

   STEP 4: CLUSTER LABELING
   ────────────────────────
   After clustering, clusters are sorted by average monetary value
   (descending) and assigned business-meaningful labels:
     Highest monetary → "Champions"
     Next highest     → "Loyal Customers"
     Middle           → "Potential"
     Lower            → "At Risk"
     Lowest           → "Lost"

── 2.4 ALTERNATIVES CONSIDERED ───────────────────────────────────────────────

   - DBSCAN: Good for arbitrary-shaped clusters but doesn't guarantee a fixed
     number of segments, making label assignment unpredictable.
   - Hierarchical Clustering: More flexible but computationally expensive
     O(n²) and harder to implement auto-labeling.
   - Gaussian Mixture Models: Would allow soft assignments (probability of
     belonging to each segment) but adds complexity without clear business
     benefit in our use case.
   - Manual RFM Scoring: Traditional approach using quantile-based scores.
     Rejected because it's rigid and doesn't adapt to the data distribution.

   3. PRODUCT RECOMMENDATIONS (ASSOCIATION RULE MINING)
================================================================================

   File: ml_models/recommender.py
   API Endpoint: GET /api/recommendations

── 3.1 WHAT IT DOES ──────────────────────────────────────────────────────────

   The recommendation engine discovers which products are frequently bought
   together ("market basket analysis"). It identifies rules like:
     "Customers who buy Milk also tend to buy Bread (confidence: 45%)"
   These rules power cross-selling suggestions and shelf placement strategy.

── 3.2 TECHNOLOGIES USED ────────────────────────────────────────────────────

   Algorithm   : Apriori-style Association Rule Mining (custom implementation)
   Metrics     : Support, Confidence, and Lift
   Library     : Custom Python implementation using itertools and collections

── 3.3 HOW IT WORKS ──────────────────────────────────────────────────────────

   STEP 1: BASKET CONSTRUCTION
   ────────────────────────────
   Transactions are grouped into "baskets" — sets of products purchased
   together in a single shopping trip:
     - Primary grouping: by basket_id (if available in the dataset)
     - Fallback grouping: by (customer_id, date) — assumes all purchases
       by the same customer on the same day form one basket.
     - Baskets with fewer than 2 items are discarded (no co-occurrence to
       analyze).

   STEP 2: ITEM FREQUENCY COUNT
   ─────────────────────────────
   Count how often each product appears across all baskets. Products
   appearing in fewer than 15 baskets (min_support_count=15) are filtered
   out as too infrequent for reliable rules.

   STEP 3: PAIR FREQUENCY COUNT
   ─────────────────────────────
   For each basket, generate all 2-item combinations of frequent items.
   Count how often each pair co-occurs. Pairs appearing in fewer than 5
   baskets (min_support_count=5) are filtered out.

   STEP 4: RULE GENERATION WITH METRICS
   ─────────────────────────────────────
   For each frequent pair (A, B), generate two rules: A→B and B→A.

     • Support = P(A ∩ B) = pair_count / total_baskets
       "How often does this combination appear overall?"
       Example: Milk & Bread appear together in 12% of all baskets.

     • Confidence = P(B|A) = pair_count / count(A)
       "Given someone bought A, how likely are they to also buy B?"
       Example: 45% of people who buy Milk also buy Bread.

     • Lift = Confidence / P(B) = confidence / (count(B) / total_baskets)
       "How much more likely is B purchased when A is present vs. random?"
       Lift > 1 = positive association; Lift = 1 = no relationship.
       Example: Lift of 2.3 means buying Milk makes Bread 2.3x more likely.

   Rules with confidence < 10% (min_confidence=0.1) are discarded.
   Final rules are sorted by Lift (strongest associations first).

   WHY APRIORI-STYLE MINING:
     - It's the gold standard for market basket analysis in retail. Well-
       understood, interpretable, and directly actionable.
     - The custom implementation avoids heavy dependencies like mlxtend while
       remaining efficient for our dataset size (~15K transactions).
     - Support/confidence/lift are universally understood metrics that
       business stakeholders can interpret without data science expertise.
     - 2-item rules (pair mining) balance simplicity with utility. 3-item
       rules are exponentially more expensive and rarely actionable in a
       supermarket context.

── 3.4 OUTPUT ────────────────────────────────────────────────────────────────

   - Top 100 association rules (ranked by lift)
   - Top 20 product suggestions derived from high-lift rules, each with a
     human-readable reason like "Frequently bought with [Product Name]"

── 3.5 ALTERNATIVES CONSIDERED ───────────────────────────────────────────────

   - mlxtend Apriori: Full Apriori implementation but adds a dependency.
     Our custom solution is leaner and sufficient for 2-item rules.
   - FP-Growth: More efficient than Apriori for large datasets. Not needed
     here — our dataset processes in under 2 seconds.
   - Collaborative Filtering: Suitable for personalized recommendations but
     requires user session history and a much larger dataset.
   - Matrix Factorization (SVD): Powerful for implicit feedback but overkill
     for a supermarket where the goal is "what goes with what" rather than
     personalized taste prediction.

   4. ANOMALY DETECTION
================================================================================

   File: ml_models/anomaly_detection.py
   API Endpoint: GET /api/anomalies

── 4.1 WHAT IT DOES ──────────────────────────────────────────────────────────

   The anomaly detection module monitors daily sales patterns and flags
   days with unusual activity — either unexpected spikes (e.g., a sudden
   rush) or drops (e.g., a supply chain disruption). Each anomaly is
   classified by type (Spike/Drop) and severity (High/Medium).

── 4.2 TECHNOLOGY USED ──────────────────────────────────────────────────────

   Algorithm   : Isolation Forest
   Library     : scikit-learn (sklearn.ensemble.IsolationForest)

── 4.3 HOW IT WORKS ──────────────────────────────────────────────────────────

   STEP 1: DAILY FEATURE ENGINEERING
   ──────────────────────────────────
   Raw transaction data is aggregated into daily summaries with 8 features:

     Base features (per day):
       • total_sales       — Sum of all transaction revenue
       • total_quantity     — Total units sold
       • num_transactions   — Count of distinct transactions
       • avg_transaction_value — Mean revenue per transaction
       • unique_products    — Number of distinct products sold
       • unique_customers   — Number of distinct customers

     Rolling features:
       • sales_7d_avg       — 7-day rolling average of total_sales
       • sales_deviation    — Difference between today's sales and the
                              7-day average (measures how "unusual" a day is)
       • quantity_7d_avg    — 7-day rolling average of total_quantity

   WHY THESE FEATURES:
     - They capture multiple dimensions of "normal" behavior. A day could be
       anomalous in revenue but normal in quantity (e.g., one expensive item
       sold), or anomalous in customer count but normal in revenue.
     - Rolling averages provide local context — what's "normal" adapts over
       time rather than being fixed.
     - The deviation feature explicitly encodes "how different is today from
       recent history," which is exactly what anomaly detection targets.

   STEP 2: ISOLATION FOREST MODEL
   ───────────────────────────────
   Isolation Forest is an unsupervised anomaly detection algorithm. Unlike
   other methods that try to profile "normal" behavior, it directly isolates
   anomalies:

     Parameters:
       • contamination = 0.05 — We expect approximately 5% of days to be
         anomalous. This controls the decision threshold.
       • random_state = 42 — Reproducibility.
       • n_estimators = 100 — Number of isolation trees in the ensemble.

     Algorithm Principle:
       1. Randomly select a feature and a random split value.
       2. Recursively partition the data (like building a random decision
          tree).
       3. Anomalies are isolated in fewer splits (they're "easy to
          separate" from the rest of the data because they're outliers).
       4. The anomaly score = average path length across all 100 trees.
          Shorter path → more anomalous.

   WHY ISOLATION FOREST:
     - Unsupervised: No labeled anomaly data required. In retail, anomalies
       are rare and diverse — it's impractical to label them.
     - Handles multivariate data naturally. Unlike z-score based methods
       (which check each feature independently), Isolation Forest captures
       anomalies that are only visible when multiple features are considered
       jointly.
     - Scales well — linear time complexity O(n × t × log(n)) where t is
       the number of trees. Trains in milliseconds on 365 days of data.
     - No distributional assumptions — doesn't assume the data follows a
       Gaussian distribution (sales data rarely does).
     - The contamination parameter gives intuitive control: "flag the top
       5% most unusual days."

   STEP 3: ANOMALY CLASSIFICATION
   ───────────────────────────────
   After detection, each anomaly is further classified:

     Type:
       - "Spike" if sales_deviation > 0 (sales above the 7-day average)
       - "Drop" if sales_deviation ≤ 0 (sales below the 7-day average)

     Severity:
       - "High" if absolute deviation > median of all anomaly deviations
       - "Medium" otherwise

── 4.4 OUTPUT ────────────────────────────────────────────────────────────────

   - List of anomalous days with date, type, severity, and detailed metrics
   - Summary counts: total anomalies, number of spikes, number of drops
   - Full daily summary (last 60 days) for chart visualization

── 4.5 ALTERNATIVES CONSIDERED ───────────────────────────────────────────────

   - Z-Score / Statistical Tests: Simple but only works per-feature, misses
     multivariate anomalies. Also assumes normality.
   - One-Class SVM: Effective but computationally expensive and requires
     careful kernel/hyperparameter tuning.
   - Local Outlier Factor (LOF): Good for density-based anomalies but
     doesn't produce a global anomaly score, harder to set thresholds.
   - Autoencoders: Powerful for high-dimensional anomaly detection but
     overkill for 8 features and requires neural network infrastructure.
   - DBSCAN: Detects noise points but designed for clustering, not anomaly
     scoring.

   5. DYNAMIC PRICING ENGINE
================================================================================

   File: ml_models/dynamic_pricing.py
   API Endpoint: GET /api/pricing

── 5.1 WHAT IT DOES ──────────────────────────────────────────────────────────

   The dynamic pricing engine analyzes each product's demand velocity, stock
   health, and shelf life risk to suggest price adjustments. It recommends
   one of three actions: Increase, Decrease, or Hold — with a confidence
   score and human-readable justification for each decision.

── 5.2 TECHNOLOGY USED ──────────────────────────────────────────────────────

   Approach    : Rule-Based Pricing Engine (Heuristic AI)
   Libraries   : pandas + numpy (for metric computation)

   NOTE: This module is NOT a machine learning model in the strict sense.
   It uses a deterministic rule-based system informed by data-driven metrics.
   It is included here because it represents an AI-driven decision system
   that leverages data analysis to automate pricing intelligence.

── 5.3 HOW IT WORKS ──────────────────────────────────────────────────────────

   STEP 1: DEMAND METRIC COMPUTATION
   ──────────────────────────────────
   For each product, the engine computes:

     • recent_quantity        — Total units sold in the last 30 days
     • recent_revenue         — Revenue from the last 30 days
     • recent_transactions    — Number of distinct sales in 30 days
     • total_quantity         — All-time total units sold
     • avg_quantity_per_day   — Average daily demand across entire history
     • current_stock          — Current inventory level
     • reorder_point          — Minimum stock level before reorder trigger
     • days_remaining         — Estimated days until stockout
                                (current_stock / avg_quantity_per_day)

   STEP 2: PRICING RULES
   ──────────────────────
   Four decision rules are evaluated in priority order:

     RULE 1: Low Stock + High Demand → INCREASE PRICE
       Trigger: stock ≤ reorder_point AND recent demand > 20× avg daily
       Action: Increase price by 5–15% (proportional to stock deficit)
       Confidence: 80%
       Rationale: Scarce supply + strong demand = raise prices to manage
       demand and preserve margin while stock is replenished.

     RULE 2: Critical Stock → PREMIUM PRICING
       Trigger: days_remaining < 7 AND recent demand > 25× avg daily
       Action: Increase price by 12%
       Confidence: 85%
       Rationale: Near-stockout conditions with sustained demand justify
       premium pricing to maximize revenue from remaining inventory.

     RULE 3: Overstocked + Low Demand → MARKDOWN
       Trigger: stock > 3× reorder_point AND recent demand < 15× avg daily
       Action: Decrease price by 5–20% (proportional to overstock ratio)
       Confidence: 75%
       Rationale: Excess inventory ties up capital and risks spoilage.
       Price reduction stimulates demand and clears slow-moving stock.

     RULE 4: Short Shelf Life → CLEARANCE
       Trigger: shelf_life_days ≤ 7 AND days_remaining > 14
       Action: Decrease price by 15%
       Confidence: 70%
       Rationale: Perishable items approaching expiry must be sold quickly
       to avoid waste. Price cuts prevent disposal losses.

     DEFAULT: HOLD
       If no rule triggers, maintain current price.
       Confidence: 50%

   WHY RULE-BASED (NOT ML):
     - Pricing decisions in supermarkets have well-understood business logic.
       Rules encoding supply-demand economics are transparent, auditable,
       and trustworthy — critical for pricing decisions.
     - No training data needed for pricing labels (we'd need historical
       "correct" prices to train a model, which don't exist).
     - Fully deterministic and explainable — every suggestion comes with a
       plain-English reason. Regulators and management can understand exactly
       why a price was changed.
     - Rule thresholds can be easily adjusted by non-technical staff without
       retraining a model.
     - Avoids the "black box" problem — a neural network suggesting a 15%
       price increase with no explanation would not be trusted by store
       managers.

── 5.4 ALTERNATIVES CONSIDERED ───────────────────────────────────────────────

   - Reinforcement Learning: Optimal for dynamic pricing over time (learn
     optimal prices by trial and error). But requires live deployment, real
     customer responses, and risks revenue loss during exploration.
   - Price Elasticity Regression: Estimate demand curves and compute profit-
     maximizing prices. Requires clean price-change history (A/B tests) that
     we don't have.
   - Gradient Boosting (XGBoost): Could predict optimal price given features,
     but needs labeled training data (price → outcome mapping).

   6. SUPPORTING LIBRARIES & INFRASTRUCTURE

── 6.1 DATA PROCESSING ──────────────────────────────────────────────────────

   PANDAS (pandas)
   ────────────────
   Used extensively across ALL 5 ML modules for:
     - Loading CSV data (read_csv)
     - Data merging (merge, join)
     - Groupby aggregations (groupby().agg())
     - Date/time manipulation (pd.to_datetime, .dt accessor)
     - Missing data handling (fillna, reindex)
     - Rolling window calculations (rolling())

   WHY PANDAS:
     - De facto standard for tabular data manipulation in Python.
     - Expressive API for complex transformations in few lines of code.
     - Tight integration with scikit-learn and statsmodels.

   NUMPY (numpy)
   ──────────────
   Used for:
     - Numerical array operations (np.maximum, np.round, np.array)
     - Random noise generation (np.random.normal in seasonal naive)
     - Standard deviation computation (np.std)
     - Value clipping (np.maximum to prevent negative forecasts)

   WHY NUMPY:
     - Foundation of Python's scientific computing ecosystem.
     - Vectorized operations are orders of magnitude faster than loops.
     - Required dependency of both pandas and scikit-learn.

── 6.2 MACHINE LEARNING FRAMEWORK ───────────────────────────────────────────

   SCIKIT-LEARN (sklearn)
   ──────────────────────
   Components used:
     - KMeans (sklearn.cluster.KMeans) — Customer segmentation clustering
     - StandardScaler (sklearn.preprocessing.StandardScaler) — Feature scaling
     - IsolationForest (sklearn.ensemble.IsolationForest) — Anomaly detection

   WHY SCIKIT-LEARN:
     - The most widely-used ML library in Python. Battle-tested, well-
       documented, and provides consistent API design across all estimators.
     - Covers traditional ML comprehensively without the overhead of deep
       learning frameworks (TensorFlow, PyTorch).
     - Lightweight installation — no GPU required.
     - Excellent for our use case: structured tabular data with well-defined
       problem types (clustering, outlier detection).

   STATSMODELS (statsmodels)
   ─────────────────────────
   Components used:
     - ExponentialSmoothing (statsmodels.tsa.holtwinters)
     - SARIMAX (statsmodels.tsa.statespace.sarimax)

   WHY STATSMODELS:
     - The premier Python library for statistical time-series modeling.
     - Provides classical forecasting models (ARIMA, Holt-Winters, SARIMAX)
       that are well-suited for business demand forecasting.
     - Includes automatic parameter optimization for exponential smoothing.
     - More interpretable than deep learning alternatives for time-series.

── 6.3 MODEL PERSISTENCE ────────────────────────────────────────────────────

   JOBLIB (joblib)
   ────────────────
   Used to serialize (save) and deserialize (load) trained ML models and
   their results to .joblib files on disk.

   Files produced:
     - ml_models/saved/demand_forecasts.joblib
     - ml_models/saved/customer_segments.joblib
     - ml_models/saved/recommendations.joblib
     - ml_models/saved/anomaly_detection.joblib
     - ml_models/saved/dynamic_pricing.joblib

   WHY JOBLIB:
     - Specialized for serialization of large numpy arrays and scikit-learn
       objects. Faster and more compact than Python's built-in pickle.
     - Used by scikit-learn internally — seamless compatibility.
     - Supports compression for smaller file sizes.
     - Simple API: joblib.dump(obj, path) / joblib.load(path).


================================================================================
   7. MODEL PERSISTENCE & SERVING ARCHITECTURE
================================================================================

── 7.1 TRAINING PIPELINE ────────────────────────────────────────────────────

   All models are trained via ml_models/train_all.py, which orchestrates:
     1. Demand Forecasting → demand_forecasts.joblib
     2. Customer Segmentation → customer_segments.joblib
     3. Product Recommendations → recommendations.joblib
     4. Anomaly Detection → anomaly_detection.joblib
     5. Dynamic Pricing → dynamic_pricing.joblib

   Training can be triggered:
     - Manually via: python ml_models/train_all.py
     - Via API endpoint: POST /api/ml/retrain (runs the script as subprocess)
     - Automatically after data upload through the frontend Data Setup panel

── 7.2 SERVING ARCHITECTURE ─────────────────────────────────────────────────

   The architecture follows an "offline training, online serving" pattern:

     TRAINING PHASE (Offline):
       CSV Data → pandas processing → Model training → joblib.dump()

     SERVING PHASE (Online):
       API Request → joblib.load() → Return precomputed results → JSON

   This design means:
     - API responses are instantaneous (no model inference at request time)
     - Training can take as long as needed without blocking the dashboard
     - Models only retrain when explicitly triggered (data upload or manual)

   WHY THIS ARCHITECTURE:
     - Supermarket predictions don't change minute-to-minute. Daily or
       weekly retraining is sufficient.
     - Precomputed results ensure sub-100ms API response times.
